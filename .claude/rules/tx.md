# The TX side (media/tx)

- **Module layout** (#360, after #300's `subscribe` split): `tx.rs` keeps the constants, `TxShared`/`Control`, `Plan`, the seqlocked `Cell`, the per-slot counts (`LaneStats`, `LaneCounts`, `count_send`) and `nanos`; `table.rs` the control side's `TxTable`/`TxFlow` (`multicast.rs` adds the multicast flows to it); `schedule.rs` `Schedule` and the time helpers (`ns_of`, `send_clock`, `flow_latency_ns`, `over_latency`); `thread.rs` the TX thread (`Lane`, `Transmitter` and its pass, `send_one`, `spawn`, the loops and the relay escape); `priority.rs` the OS thread calls (`ask_priority`, the Windows priority mapping, `place`, `pin_to_cpu`) beside `take_priority` and the MMCSS record. Every public name is re-exported at `media::tx::`, so callers and siblings (`use super::ns_of`) never name the file. A `Transmitter` field a sibling's `impl Transmitter` reads (`split.rs`, `shift.rs`) is `pub(super)`. The tests read names through `use super::*`, so a name only they use is a `#[cfg(test)]` import in `tx.rs` (`escape_through`, `run_relay`, `run_with`, `send_one`, `pin_to_cpu`; `ask_priority` only under `cfg(all(test, windows))`). A function that moves files takes its `.cargo/mutants.toml` `exclude_re` path along (`tx/thread.rs.*send_one`, `tx/priority.rs.*unthrottle`).
- **The TX pull** (#363, `tx/fill.rs`): an app's TX `Process` (dlink's `TxPull`, behind `Rated` when converting) claimed once with `TxShared::claim_fill` before the TX thread builds its state (`Transmitter::new` takes it after `host_for_tx` closes the claims, under the control lock), so each engine ring keeps ONE writer: the pump or the TX thread, never both (`engine_channels` refuses a channel in both maps; `claim_fill` itself never sees the pump's map, so start through `Embedded::start_tx_pulling`). Each pass runs `fill_due` before `send_due` (`step` and `before_wait`'s last pass alike), on the pump's own `stream::Blocks` with the schedule's margin set to the fill's reach (W + the flows' largest lag bound, `Transmitter::reach_lag`: the advertised latency, or a receiver's stated one when longer, #426); D for the stamp is the real W (`Timing::offset`). A new P (`RxShared::playout`) restarts it (counted); a new bound only moves the reach (`Blocks::with_margin`: a restart would reset a `Rated` behind the pull and glitch). A start or restart is the pump's bootstrap (`fresh`, no catch-up): starting W earlier (the block stamped now) fills the W of holes a TX restart sends first, but pops W in one pass right after the player's resync prime and leaves its FIFO W under target (the app buffer short until braked back, ~300 s): tried and reverted in #363's review. The pulled path is in the release soak (`soak.rs` `Tx::Pulled`, `Tx::PulledTxStall`; the harness's `TxSide` runs inside the app on the pump's path or alone behind its own `Rated` on the TX thread's). A re-anchor goes through `re_anchored` with the media clock (not the send clock) and is judged within W (`with_margin(W)` around `re_anchor`), never the reach, or the fill and the pump leave the engine line apart. The fill's faults/restarts warn once a second from the daemon tick (`FillWatch`, `TX_PULL_WARNING`). `wake_ns` includes the fill's next due time, so the TX thread wakes at the pump's times. A whole-device proof is `dlink/tests/tx_pull.rs` (pump stalls 10-20 ms against a steady 10 ms app writer: 0 off, 0 TX holes, 0 writes after send, 0 underruns); a fill unit test that needs the TX thread to stay under its 1 ms test latency steps under 1 ms apart (1.5 ms restarts the flows' schedule, which is not the fill's doing).
- **The socket past the qdisc after a NIC re-create** (#414, `tx/direct.rs`): `TxShared::follow_direct` moves `Direct`'s per-send interface index (an `AtomicI32`, the TX thread's only read of it) from the TX interface watch, beside the flow sockets' `send_on_again` (`keep_send_interface`, `tx/multicast.rs`); the INFO line is `direct::FOLLOWED`, which CI's re-create test greps. A test builds a device past the qdisc with `TxShared::new(..).with_direct(Direct::stand_in(index), nic)` (cfg(test), Linux): `.claude/rules/multicast.md`.
- **The host frame sender's NIC after a re-create** (#417, `tx/host.rs`): the neighbour rows count only on our NIC's interface index, `HostPath::ifindex` (an `AtomicU32`, started from `HostNic.ifindex`, which stays the start value; read by `set_host_macs` on the control side only). `TxShared::follow_host(new_index)` moves it from the same TX watch (`keep_send_interface`, beside `send_on_again` and `follow_direct`), with the index the watch's list just gave (`Membership::keep_with` hands the act the `Rejoin`); INFO `host::HOST_FOLLOWED` once per move, then the slots' MACs from the rows already read. A test drives it on Linux with `use_frame_sender` + `set_neighbours` + `membership::fake::Fake` (`tx/host/tests/follow.rs`).
- **A flow's lag bound** (#426, `tx/schedule.rs`): a lane restarts its schedule past `Schedule::bound`, the longer of our advertised latency (`max_lag`) and its receiver's stated one (`receiver_lag`, from `receiver_lag(receiver_ns, rate)` each pass in `send_due`, capped at `device::MAX_LATENCY_SAMPLES`, the engine ring's reach; 0 while unknown or multicast). A receiver plays a flow at its own latency, at least ours (the rule `PassClock::late_threshold` counts late packets by), so a packet within it is still worth sending. The restart line's `max_lag` is the bound it was judged by, and its `slot` the lane (#427: `Schedule::slot`, set where `send_due` builds the lane's schedule; a test outside the crate sets it on a `bootstrap` result, the struct has a private field). A re-anchor's room (`Schedule::re_anchor`) stays on our latency: it only tells a pass that already restarted at the new time from a moved one.
- **"Our flow arrives late" at a receiver** (#424): first split send-side from after-send. Our side: the lane's `late_bins` (past due = stamp + fpp + `tx_margin_ns`) and `age_max_us` on the local status endpoint (`status` over TCP 127.0.0.1, port in the `local status endpoint` start line). The receiver's side, when it runs dstack: its `rx` entry's `latency`, `playout` and `late_after` are SAMPLES (`late_after` = playout + block: 864 at 96 kHz is 9.0 ms, not 864 µs), and a receiver stating 1000 µs in its flow request still plays our flow at max(own, advertised) = P. If the receiver's late packets are older than anything our `late_bins` sent, the delay sits after `sendto` (#424/#425: songplayer-pp's Dante VLAN shares a USB 2.5GbE with ~200 Mbit/s of NDI; each Dante packet waits behind an NDI frame in the NIC's one send queue) and no TX schedule or wait change removes it.
