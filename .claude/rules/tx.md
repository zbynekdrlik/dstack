# The TX side (media/tx)

- **Module layout** (#360, after #300's `subscribe` split): `tx.rs` keeps the constants, `TxShared`/`Control`, `Plan`, the seqlocked `Cell`, the per-slot counts (`LaneStats`, `LaneCounts`, `count_send`) and `nanos`; `table.rs` the control side's `TxTable`/`TxFlow` (`multicast.rs` adds the multicast flows to it); `schedule.rs` `Schedule` and the time helpers (`ns_of`, `send_clock`, `flow_latency_ns`, `over_latency`); `thread.rs` the TX thread (`Lane`, `Transmitter` and its pass, `send_one`, `spawn`, the loops and the relay escape); `priority.rs` the OS thread calls (`ask_priority`, the Windows priority mapping, `place`, `pin_to_cpu`) beside `take_priority` and the MMCSS record. Every public name is re-exported at `media::tx::`, so callers and siblings (`use super::ns_of`) never name the file. A `Transmitter` field a sibling's `impl Transmitter` reads (`split.rs`, `shift.rs`) is `pub(super)`. The tests read names through `use super::*`, so a name only they use is a `#[cfg(test)]` import in `tx.rs` (`escape_through`, `run_relay`, `run_with`, `send_one`, `pin_to_cpu`; `ask_priority` only under `cfg(all(test, windows))`). A function that moves files takes its `.cargo/mutants.toml` `exclude_re` path along (`tx/thread.rs.*send_one`, `tx/priority.rs.*unthrottle`).
- **The TX pull** (#363, `tx/fill.rs`): an app's TX `Process` (dlink's `TxPull`, behind `Rated` when converting) claimed once with `TxShared::claim_fill` before the TX thread builds its state (`Transmitter::new` takes it after `host_for_tx` closes the claims, under the control lock), so each engine ring keeps ONE writer: the pump or the TX thread, never both (`engine_channels` refuses a channel in both maps; `claim_fill` itself never sees the pump's map, so start through `Embedded::start_tx_pulling`). Each pass runs `fill_due` before `send_due` (`step` and `before_wait`'s last pass alike), on the pump's own `stream::Blocks` with the schedule's margin set to the fill's reach (W + the flows' largest lag bound, `Transmitter::reach_lag`: the advertised latency, or a receiver's stated one when longer, #426); D for the stamp is the real W (`Timing::offset`). A new P (`RxShared::playout`) restarts it (counted); a new bound only moves the reach (`Blocks::with_margin`: a restart would reset a `Rated` behind the pull and glitch). A start or restart is the pump's bootstrap (`fresh`, no catch-up): starting W earlier (the block stamped now) fills the W of holes a TX restart sends first, but pops W in one pass right after the player's resync prime and leaves its FIFO W under target (the app buffer short until braked back, ~300 s): tried and reverted in #363's review. The pulled path is in the release soak (`soak.rs` `Tx::Pulled`, `Tx::PulledTxStall`; the harness's `TxSide` runs inside the app on the pump's path or alone behind its own `Rated` on the TX thread's). A re-anchor goes through `re_anchored` with the media clock (not the send clock) and is judged within W (`with_margin(W)` around `re_anchor`), never the reach, or the fill and the pump leave the engine line apart. The fill's faults/restarts warn once a second from the daemon tick (`FillWatch`, `TX_PULL_WARNING`). `wake_ns` includes the fill's next due time, so the TX thread wakes at the pump's times (a pump with the RX hand-off lead, #476, wakes H earlier; the fill runs without the lead, `TxFill::new`, so it wakes H after it and both stamp W after their own wake). A whole-device proof is `dlink/tests/tx_pull.rs` (pump stalls 10-20 ms against a steady 10 ms app writer: 0 off, 0 TX holes, 0 writes after send, 0 underruns); a fill unit test that needs the TX thread to stay under its 1 ms test latency steps under 1 ms apart (1.5 ms restarts the flows' schedule, which is not the fill's doing).
- **The socket past the qdisc after a NIC re-create** (#414, `tx/direct.rs`): `TxShared::follow_direct` moves `Direct`'s per-send interface index (an `AtomicI32`, the TX thread's only read of it) from the TX interface watch, beside the flow sockets' `send_on_again` (`keep_send_interface`, `tx/multicast.rs`); the INFO line is `direct::FOLLOWED`, which CI's re-create test greps. A test builds a device past the qdisc with `TxShared::new(..).with_direct(Direct::stand_in(index), nic)` (cfg(test), Linux): `.claude/rules/multicast.md`.
- **The host frame sender's NIC after a re-create** (#417, `tx/host.rs`): the neighbour rows count only on our NIC's interface index, `HostPath::ifindex` (an `AtomicU32`, started from `HostNic.ifindex`, which stays the start value; read by `set_host_macs` on the control side only). `TxShared::follow_host(new_index)` moves it from the same TX watch (`keep_send_interface`, beside `send_on_again` and `follow_direct`), with the index the watch's list just gave (`Membership::keep_with` hands the act the `Rejoin`); INFO `host::HOST_FOLLOWED` once per move, then the slots' MACs from the rows already read. A test drives it on Linux with `use_frame_sender` + `set_neighbours` + `membership::fake::Fake` (`tx/host/tests/follow.rs`).
- **A flow's lag bound** (#426, `tx/schedule.rs`): a lane restarts its schedule past `Schedule::bound`, the longer of our advertised latency (`max_lag`) and its receiver's stated one (`receiver_lag`, from `receiver_lag(receiver_ns, rate)` each pass in `send_due`, capped at `device::MAX_LATENCY_SAMPLES`, the engine ring's reach; 0 while unknown or multicast). A receiver plays a flow at its own latency, at least ours (the rule `PassClock::late_threshold` counts late packets by), so a packet within it is still worth sending. The restart line's `max_lag` is the bound it was judged by, and its `slot` the lane (#427: `Schedule::slot`, set where `send_due` builds the lane's schedule; a test outside the crate sets it on a `bootstrap` result, the struct has a private field). A re-anchor's room (`Schedule::re_anchor`) stays on our latency: it only tells a pass that already restarted at the new time from a moved one.
- **"Our flow arrives late" at a receiver** (#424): first split send-side from after-send. Our side: the lane's `late_bins` (past due = stamp + fpp + `tx_margin_ns`) and `age_max_us` on the local status endpoint (`status` over TCP 127.0.0.1, port in the `local status endpoint` start line). The receiver's side, when it runs dstack: its `rx` entry's `latency`, `playout` and `late_after` are SAMPLES (`late_after` = playout + block: 864 at 96 kHz is 9.0 ms, not 864 µs), and a receiver stating 1000 µs in its flow request still plays our flow at max(own, advertised) = P. If the receiver's late packets are older than anything our `late_bins` sent, the delay sits after `sendto` (#424/#425: songplayer-pp's Dante VLAN shares a USB 2.5GbE with ~200 Mbit/s of NDI; each Dante packet waits behind an NDI frame in the NIC's one send queue) and no TX schedule or wait change removes it.
- **A media loop's sleep is bounded by its own read** (#440, a gen3 pump asleep three days): a target computed from a pass's time read sleeps through `PtpClock::sleep_until_within(target, target - read)` (`split::timed_sleep` takes the pass's read; the pump loop does the same), never a bare `sleep_until`: the clocks re-read their time base in the sleep, so a re-anchor between the read and the sleep (a new k, a follower step, a source switch) moved the monotonic deadline by the whole step back (-43.9 days). A new `PtpClock` overrides `sleep_until_within` with ONE read of its base; the default bounds through one `now_ns` read.
- **A clock gone back = a wait past the re-anchor's room** (#440's residual window, ROZHODNUTÉ 19.11): `Blocks::next` re-bootstraps `ClockBack` when the next block is more than W + B ahead, `Schedule::due_after` restarts when the next stamp is more than `Schedule::ahead_limit` (the bound, at least `Schedule::block`, and a packet) ahead; `DISCONTINUITY` (2 s) is gone. Each limit EQUALS its `re_anchor` room, so a moved schedule is never read as clock-back: change one, change the other (`a_schedule_moved_to_the_edge_of_its_room_waits`, `a_re_anchor_at_the_edge_of_the_room_still_moves`). The TX block lives on the schedule only (`block`, set where `send_due` builds the lane's schedule, as `slot`; `re_anchor` reads it), never a second argument. Near media time 0 no block starts before 0, so a bootstrap's first block is due at B + P (B + P - H with the hand-off lead, `Timing::first_due`, #476): `next` measures from `now.max(Timing::first_due())`, or a P > W start re-bootstraps forever inside one pass (`a_schedule_near_time_0_waits_its_first_block`). **The one-pass mark** (ROZHODNUTÉ 19.11): the epoch follows the raced pass with the step back, and `re_anchor` used to move the already-restarted schedule the step back again (a second restart: pump `late`, the step's blocks in `missed`, a wake late by the step, read like #440's stall). A clock-back restart now marks the schedule (`Blocks`, `Schedule`; the TX pull's fill keeps `next`'s re-bootstrapped value, never `fresh`, so its mark survives); the next re-anchor keeps a marked schedule for a step BACK, read BEFORE the grid check (fpp 64 on a block of 32 takes half the steps off its grid), and spends the mark either way; a pass at the same epoch or with the clock not ready spends it (`Pump::media`'s plain arm, `Transmitter::step` -> `Transmitter::unmark`). The re-anchor lines log `marked`. Never a position-only rule: it also keeps a schedule that only waited a step of W..W+B and runs it off the engine line. A new pass entry point must spend the mark at its re-anchor point too (`stream/tests/clock_back.rs`, `media/tx/tests/clock_back.rs`, `fill/tests.rs::the_tx_thread_keeps_the_fill_restarted_by_a_step_back_for_one_pass`).
- **A media thread's priority on Windows is judged by its read-back** (#461, `tx/priority.rs`): MMCSS off (`HKLM\SYSTEM\CurrentControlSet\Services\MMCSS` Start=4, FOH 11.2026) still answers the join with a handle and task index 4294967295 (`NO_MMCSS_TASK`) and raises nothing. `take_priority` reads `GetThreadPriority` after the join (`thread_priority`; Windows glue `thread_priority_of_windows`, excluded by that name, Linux twin `None` pinned by a test) and the pure `joined_task` keeps a thread in MMCSS only with a real index AND a read-back above HIGHEST; `held` turns a read-back under the level asked into `refused`. GetThreadPriority returns the raw increment, so a joined thread reads 18-19 (resolume-snv, BelowNormal class: base 24/25); never compare it with a level table. The priority is NEVER set again after the join (owner ROZHODNUTÉ 20.11.2026: dsend, a fallback on FOH, takes no CPU priority from dasio; and a SetThreadPriority after a real join takes the thread out of MMCSS's band, 25 back to 8, measured). To measure such OS behaviour without a dstack build on a Windows test PC (resolume-snv), run a PowerShell `Add-Type` C# P/Invoke probe in the MCP `Shell` (a new `Thread`, read `GetThreadPriority` and `Process.GetCurrentProcess().Threads[..].BasePriority` around each call); disabling mmcss.sys needs a reboot, so the MMCSS-absent path is read from the field log (`read`) at the next restart.
- **A pump that owns no channels** (#461, `PumpStats::for_map` from the pump's own `Map` in `embed.rs`; dsend's: every TX channel pulled by the TX thread, no RX): its re-bootstrap or overrun loses no audio and logs `stream::watch::PUMP_NO_LOSS` (info, same fields, one `pump_line!` macro for both lines); `PUMP_WARNING`'s text and fields stay unchanged for a pump with channels, since consumers grep it. A pump built by `PumpStats::new` alone owns channels (33 call sites keep their behaviour).
- **Our advertised latency must fit the receiver's range** (#480, a regression of #461): a TX app's latency P goes out before any subscription as `latency_ns=` in each `_netaudio-chan` TXT record (`announce.rs`, `advertised_latency_ns`), shared by every receiver of the channel; the flow request (0x0100, `FlowRequest`) carries no latency. A receiver plays at max(own, ours) only within its own range (ARC 0x1100: 0x8302 max, 0x8306 min; `arc::control::Settings`): the site's hardware states 10.156 ms (a card, the wireless receiver) and 10.667 ms (another card), and a P past it reads "Incorrect channel latencies" in Dante Controller (the FOH Yamaha AIC128-D on dsend's 40 ms). So no TX app's default goes past 10 ms; more margin is the app's own flag (dsend `--latency-ms`), set only for receivers that accept it. Adapting P per receiver is not possible in the protocol (one advertisement per channel; a change means a re-subscribe).
- **A media thread's EEVDF slice on Linux** (#302, `tx/priority/slice.rs`): the pump and the TX thread ask `sched_runtime` = 200 us with `sched_setattr` (libc has `sched_attr`, 48 bytes, and the `SYS_` numbers, no wrapper) after `ask_priority`, and only when the read policy is SCHED_OTHER. Keep only `SCHED_FLAG_RESET_ON_FORK` from the read flags (util-clamp flags with size 48 are EINVAL). A kernel before 6.12 TAKES the request (returns 0) and reads back 0: that is `ignored` (info), not a refusal; only `refused` warns, once a device (`Scheduling::first_slice_warning`). A test that writes a thread's attributes or asserts its starting policy puts the thread on SCHED_OTHER first (`other_at_nice_3`): under `chrt -f 10` (the load practice) a spawned thread inherits SCHED_FIFO and a SCHED_OTHER-shaped write with priority 0 is EINVAL. `tx/priority.rs.*take_priority` in `.cargo/mutants.toml` also excludes `take_priority_asked` on purpose; the slice decision is `slice::request` over closures.
- **A frame-sender host's socket sends go to the relay thread** (#485, `tx/outbox.rs`): on FOH one Winsock send to the on-PC receiver took ~1.4 ms and held the pass's NIC batch. `send_due` queues each socket packet (`Outbox::push`, an entry per packet with the pass's `PassClock`, a per-entry Mutex nobody waits on: no unsafe, no allocation) and publishes after `Batch::flush`; the relay thread sends them (`Relay::serve_with`'s idle step, parked otherwise; `publish` and `hand_over` unpark it), and drains after each pass it covers. The queue is used only while a thread serves it (`Outbox::serving`), so a test that drives `Transmitter::step` alone still sends inline; a test that wants the queue serves it from its own thread (`outbox().serve_here()` in the crate, `TxShared::serve_socket_sends_here` + `send_queued` outside, as `tests/hot_path.rs`). A slot with entries pending skips the NIC batch (`Outbox::pending`), so a flow never passes itself across the two paths; only a full queue can reorder (counted `full`, warned once a second, `late::QUEUE_FULL`). While the relay thread covers an escape it sends NONE of the queue (a covered pass would wait behind the slow send again: review of #485), and `before_wait`'s last pass queues without publishing (`send_due(.., publish: false)`), so the relay is not inside a send at the offer. A queued packet's late count is the queue's (`Outbox::late`, the late line's `queued`) and its clock drops `escaped_ns`: never `relayed`/`since_escape` (#177's escape relay). A test that spawns the TX or relay thread inside `thread::scope` stops it from a drop guard (`OnDrop` in `socket_stall.rs`): a failed assert otherwise hangs the scope's join forever. A slow socket send in a test: `TxShared::stall_socket_send(ns)` (doc-hidden, one-shot spin on whichever thread sends; `tx/tests/socket_stall.rs` drives the real TX + relay threads on `StepClock`). That test runs ONCE and judges a miss (v0.6.223): it takes `tx_thread_stats().take_look()` after each `run_to`, and a miss still past 250 us once the step's hold (longest pass less its largest CPU time) is taken off is OURS, else RUNNER; both fail. Never a retry loop in a timing test.
