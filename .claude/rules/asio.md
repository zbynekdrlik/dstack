# The ASIO host (dstack-asio, #243)

- **Lifted from SongPlayer, byte for byte where it writes:** `format::Sample::encode` is SongPlayer's `asio_format` encode on `f64`; `an_f32_widened_to_f64_writes_songplayers_bytes` pins it against SongPlayer's formula written out in the test. Never change the rounding or the full scales: SongPlayer moves onto this crate with no behaviour change.
- **Every decision is pure and Linux-tested; `win.rs` only calls the driver** and is excluded from the mutation gate (`.cargo/mutants.toml`). A new Windows decision goes into `state`, `device`, `engine` or `runner` with a test, never into `win.rs`. Times are ns (SongPlayer's are 100 ns).
- **The buffer switch is `Engine`:** decode the used inputs, run the app's `Process` under `catch_unwind`, encode every driver output (unmapped ones zeroed). It allocates nothing; a panic plays silence from then on and the `Runner` closes the run (`faults > 0`).
- **A process that loads an ASIO driver spawns no child** (SoundGrid resyncs on any spawn from that process, songplayer #233). dasio's instance process must keep to it.
- **Bridge targets** (#247): the ASIO buffer + one pump block by default (256 at 96 kHz: 4.0 ms). The simulated-clock tests pin ±50 ppm at the default, ±100 ppm at a set 5 ms, and at most two dropouts in the first 80 s (at about 27 s and 67 s) then none at ±100 ppm at the default (5 ppm/s slew, 60 s rate lock). Never loosen the asserts to make a default hold more.
- **The bridge simulation tests take ~17 s** (two sinc converters at 96 kHz for 180 s each): a crate test run passes the harness's 180 s background limit only with `timeout 170`; run a throwaway probe of other drifts/targets as its own `cargo test <name>` in the background and wait on its output file (never end the turn while it runs as a subagent).
- **azo 0.4.0 cross-compiles** for `x86_64-pc-windows-gnu` on dev1 (its build script runs windows-bindgen on the host): check `cargo clippy --target x86_64-pc-windows-gnu -p dstack-asio` before a push.
- **The from-ASIO figures** (#325, `bridge/age.rs`): the receiver figure is MEASURED, never modelled. `from_asio_packet_age_us` is the minute's max of `TxShared::take_app_view().age_peak_ns` (a per-lane peak of its own, `age_app_peak_ns`; never take the late watch's `take_age_peak`, it would starve it), and `from_asio_min_receiver_latency_us` = that + `RxShared::network_p99_ns()` or 200 us. The modelled block age (call period + hand-over wait; `compare_exchange(NONE, now)` at the hand-over, `swap` at the take: the pump's side, or pulled the TX thread's `FromAsio`, #364) is a diagnostic only: dasio's field read 1.9 ms modelled vs 1.0-1.4 ms real packet ages (16.11.2026). The hourly WARN comes only from a receiver's own `over_latency` rising (`BlockAge::look`, from the app's status loop, never the pump: the view locks the TX table). The status keys are dasio's (`bridge_json`). Tests drive it with `BlockAge::new(clock)` / `Bridge::with_clock` and a fake clock; a test that checks a warning's text never names a receiver after a word in it ("high" is in "higher", "old" is in the packet-age clause).
- **The to-ASIO side is pulled by the driver's buffer switch** (#307 step 2, `Bridge::pull_to_asio`): the switch pulls through dlink's `SharedPull` (an `Arc<OnceLock<SharedPull>>` the bridge, the pump's side and every driver side hold; `pull` only tries the lock), then `serve`s (the rtsan-marked part: from-ASIO feed, age, player). The pump's side feeds the to-ASIO FIFO only unpulled and only for a block with RX inputs (a pulling app's pump has none, so the moments before `pull_to_asio` push no zeros). While no driver is open the app's loop calls `Bridge::keep_pulled` (the idle drain), or the flow reads silent and is closed. Pulled, the to-ASIO player's producer chunk is the ASIO buffer (`to_asio_chunk_ns`), so a pull handed over after the first open is refused; a pull of another width than its FIFO is refused by `RxPull::new` itself (a narrower one would index past its scratch in the callback). `keep_pulled`'s period must exceed the longest driver buffer period (250 ms; 100 ms would read a 128 ms buffer as stopped). Prove a change with `tests/to_asio_pull.rs` (whole device: 31 pump stalls of 10-20 ms against a steady 256 @ 48 kHz switch, 0 underruns / 0 off; the pump-written path had 13 / 6350), `tests/to_asio_alloc.rs` and the rtsan job's `-p dstack-asio --test rtsan`. A pull unit test sends its packets after the first pull (`Start`): a new flow's first drain drops what waited in its socket as `stray` (#326).
- **`tests/to_asio_pull.rs` and load** (#307): the same class as dlink's `rx_pull.rs`. At dev1 load ~60 (other accounts' gates) it failed once with ring `holes` 3200 and 0 underruns: the sender's TX restarts, not the bridge (an underrun with no holes would be the bridge). Rerun it alone before calling it ours. Since #401 the verdict reads that itself (`SENDER` when every sender TX restart in the window slept its latency late).
- **`tests/to_asio_pull.rs`'s driver-thread witness** (#307, v0.6.155 windows-2025: 2 underruns, 2584 off, no ring hole, no pull restart): the test's "driver" thread is the bridge's consumer, and when the runner does not run it (a gap over two periods) its back-to-back catch-up switches take the depth the late switch's pull brought and the player skipped as an excess, and run the FIFO dry. A 20 ms stall of that thread every 700 switches with no pump stall gave the same 2 / 2584 on dev1. Until #396 (superseded, see below) the thread recorded its own gaps (`clock::app_monotonic_ns`) and a judged window with a driver stall was set aside and the next judged (up to `WINDOWS` = 4, about 8 s each; since #395 with 100 ms unjudged after a window set aside, a stall inside it starting it again, and a window counting underruns from before its first switch: before, a stall at a window's close charged its catch-up underrun to the next window, which read `OURS`), a failure prints `verdict RUNNER|OURS` with the stalls before each underrun. A run of 20 s instead of 12 s means one window was set aside. Since #396 the witness is dlink's shared `tests/consumer/witness.rs` (`#[path]`, with `tests/tx_restart/restarts.rs` as `mod restarts` and, since #436, `consumer/sender.rs` as `mod sender`; `tests.md`'s "shared consumer witness"): a switch later than its floor by more than a period (5.333 ms) is a stall (lateness against the schedule, not the gap), a window is set aside only when it lost audio and its verdict is not `OURS`, and holes never written after the sender's TX restarts with late sleeps read `SENDER` (#401: a temporary 12 ms TX sleep every 700 read `SENDER`, 11028 off). Hardware pacing (skipping the missed switches) was tried and rejected: the skipped time reads as a rate step to the player (134 samples off, mean depth 5.2 ms of 8).
- **The from-ASIO side is pulled by the TX thread** (#364, `Bridge::pull_from_asio` -> `bridge::FromAsio`): dlink's `TxPull` over the from-ASIO player plus `BlockAge::taken` (the modelled take now at the TX fill; the measured packet age is the TX side's, unchanged). Take it BEFORE `dante_side()` (the first player and its taker live in the pump's side until then) and before the driver's first open (the pull gets its own `Switch`, replacing the bridge's: nothing was sent through the old one yet). Then the pump's side plays no from-ASIO audio and the pump's map names no TX channel (one writer a ring). A dlink app starts it with `Link::start_pulling_with_tx` (to-ASIO pulled too) or `Link::start_tx_pulling`; dasio, which builds the device from dstack's parts (`run_bridge.rs`: `prepare_config`, `Pump::new`, `prepared.start`), claims `TxFill::new(Box::new(from), engine_tx, timing, encoding, rx)` with `media.tx.claim_fill` before `prepared.start` (CHANGELOG's port steps). `Switch::send` collects first, so after a reopen `collect()` returns only the last retired player. Prove a change with `tests/from_asio_pull.rs` (whole device, both ways and from-ASIO only, `DSTACK_TEST_LOOPBACK=1 chrt -f 10`; the pump path, `DanteSide`, read 20868 samples off / 17920 TX holes / 22 writes after send under 22 stalls, pulled 0 and the fill's `tx_pull` clean), `tests/from_asio_alloc.rs` and the rtsan job's `-p dstack-asio --test rtsan`. To measure the old path again, copy the test into a throwaway file whose `start_bridge` uses `Link::start_pulling_on` with the `DanteSide` (no `pull_from_asio`) and delete it after.
- **Per-direction targets and the margin each needs** (#382): `Spec::to_asio_app_buffer_ns` / `from_asio_app_buffer_ns` override `app_buffer_ns` per direction (`None`: as before). From-ASIO must cover the driver's callback lateness one for one (a late write while the TX thread reads on time); to-ASIO pays nothing for it (pull and play share the switch). A callback counts `late` only past a gap of two periods (`state::callback_gap_kind`), so one 1.0-1.33 ms late at 128 @ 96 kHz drained the from-ASIO FIFO unseen until the lateness bins (#386, below). The 128-frame converter calls are not a margin term: 32-frame calls at the same target hold less and at the same latency hold the same (measured, #382 issuecomment-6952521129). To measure a bridge's real latency in a simulation, have the writer push a ramp (frame index) and compare the played value with the writer's clock at the fill, less the sinc's delay.
- **The per-direction floor** (#422, dasio#190): `to_asio_app_buffer_ns` / `from_asio_app_buffer_ns` take `MIN_BRIDGE_TARGET_NS` (0.5 ms) to 150 ms, checked at `Bridge::new` (`direction_target_problem(key, ns)`, dlink's text with the key and the bridge's floor: `to_asio_app_buffer_ns: 499999 ns (0.499999 ms); 0.5 to 150 ms`); a configured shared `app_buffer_ns` keeps dlink's 1 ms (refused at the open). The default (the driver's buffer + one pump block, nothing set) is the bridge's own term and takes the bridge's floor too (#482, `Bridge::buffer_set`: dsg's 32-frame SoundGrid with 32-frame blocks at 96 kHz is 0.666666 ms both ways, refused at the open against 1 ms before; `bridge/tests/default_floor.rs`). A test's frame counts go through `chunk_ns`, which rounds each term: 16 + 32 frames at 96 kHz is 166667 + 333333 = 500000 ns, exactly the floor, not under it. A direction's own target is an `AppBuffer` `with_floor(MIN_BRIDGE_TARGET_NS)` (`Bridge::direction_buffer`), so its player plays it unclamped; dasio's `[bridge]` check and dtray's copy (`dasio::bridge::MIN_BRIDGE_TARGET_NS`, pinned equal by a Windows test) use the same range. Measured (issuecomment-6992267133, both sides pulled on simulated time with dlink's `Fifo`/`Player`, 96 kHz, 180 s a run): to-ASIO holds 0.5 ms cold at ±7.5 ppm with a 128 or 64-frame driver (0.375 drops once in the slew) and 0.125 ms seeded at ±100; from-ASIO, whose producer writes the whole driver buffer, holds 0.375 ms with a 64-frame driver and needs 0.75 ms with a 128-frame one (seeded, a dropout at each phase crossing of the clocks, every buffer / drift: 26.7 s at 50 ppm), plus its callback lateness. Cold, every target pays the slew (to-ASIO: 0.75 ms holds ±10 ppm, 1 ms ±15). `bridge/tests/floor.rs` plays both ways at the floor with a 64-frame driver, seeded ±50 ppm, 30 s (two crossings); the same run with a 128-frame driver drops out from ASIO, so it bites. Its to-ASIO side is pump-written (32-frame pushes; a pull needs a device), easier than the field's pull: the pulled floor rests on the ticket's table. To measure such a floor again: a throwaway `crates/dlink/tests/<probe>.rs` driving `Fifo::with_clock` + `Player` (`AppBuffer::with_floor(0)`) on simulated time, cases from env vars on a thread pool, `cargo test --release` (a 180 s run of two 256-tap players takes ~5 s; 168 runs ~2 min on 12 threads at dev1 load 30), deleted before the commit.
- **Callback lateness bins and the underrun line** (#386, #393): a switch's lateness is how far behind the driver's schedule line it came (`state::schedule_lag`: due one period after the last line; an on-time or early switch re-anchors the line, a late one creeps it at most period/1000, so a slow driver clock never sums into a lag), NEVER its gap minus the period: dsg's MiniFuse (128 @ 96 kHz on 1 ms USB frames, gaps 2, 1, 1 ms, a third of all switches 500-750 us) put writes 1.0-1.333 ms behind on a frame slip (two 2 ms gaps) while the gap measure read two 500-750 us callbacks, and the underrun line blamed the bridge. `state::lateness_bin(late_ns)` puts 0.25 ms or more in one of eight 0.25 ms bins (the top one open: 2.0 ms or more behind); a gap over two periods counts only as `late_callbacks` and re-anchors the line (its catch-up switches are no lateness). A test of a single late switch's bin follows it with a catch-up switch right after, or the next one on its own slot: a switch a fixed time after a late one can sit past its slot and still count behind (half a period after one 2 ms late at a 2 ms period read 1 ms). Per run like `late_callbacks` (`Counters` -> `DeviceEvents` -> `Status::late_bins`), keys `state::LATE_BIN_KEYS` (`late_250us`..`late_2000us`, the same at every buffer size). `bridge::UnderrunWatch::look` (the app's status loop, never the callback) warns on an underrun rise with the lateness over the same check. From-ASIO reads the reach (a closed bin's LOWER edge, an upper-edge rule blamed 0.75-1.0 ms at 1.333 ms; the top bin by the run's peak lateness when it rose over the check, `UnderrunCounts::late_max_us` from `Status::late_max_us`, #393: summed lateness can pass a period, else by the driver's period `UnderrunCounts::period_us`) against the target LESS the side's floor (#393 last line): the floor is half the driver period (the driver writes its whole buffer at a switch; inside #422's measured brackets, 0.667 ms in (0.625, 0.75] at 128 frames, 0.333 in (0.25, 0.375] at 64 frames with 64-frame blocks; with 32-frame blocks 64 frames held 0.125, so there it is an upper bound: the counts carry no pump block), 0 with no period known; floor + lateness is the worst case (a late write at the FIFO's low point), #422's sparse late bursts needed only the larger of the two. The driver's past two periods or when the reach alone is the target; `Cause::Target` ("the target under the side's floor plus the callbacks' lateness", wire `UnderrunCause::Driver`, no new code: an older reader refuses one) when floor + reach is; else the bridge's. The 3/4-of-target rule it replaced named dsg's 1 ms target with two 500-750 us callbacks the bridge's. To-ASIO only past two periods, unknown at a target of 0. Pin an edge with its exact integer pair (`2 * reach + period >= 2 * target`: 7999 vs 8000 us at a 5333 period, 1166 vs 1167 at 500 us late and 1333), worked out before writing the assert, and one pair at an EVEN period (2666, 256 @ 96 kHz as `UnderrunCounts::of` truncates it), where the edge is equality (an odd period never reaches it, so `>=` to `>` would pass); a test that tells the peak from the period fallback needs a target where the two read differently (4.5 ms at 2667, not 4 ms).
- **The ASRC seed** (#382, `bridge::Seed`): each open's players start from the standing locked rates at the same Dante and driver rates (`Bridge::seed_from` before the first open, `Bridge::seed()` written back by the app with `Seed::write`); `Bridge::seed` keeps the known seed while a run at other rates knows none. A seed test judges the from-ASIO correction over the first minute (`tests/asrc_seed.rs`): the pump-written to-ASIO side brakes an offset of its own start in its first 20 s, seeded or not.
- **A bridge simulation names its block starts** (#382): `Block::new(..).at(frames)` on both sides and `Bridge::with_clock` (which now clocks the FIFOs too), so the players steer on the producer's line as in the field. Without starts a 128-frame writer against 128-frame converter calls at a few ppm is phase-locked: the sampled depth steps once per ~178 s at 7.5 ppm and the rate fit locked on 0.000 ppm (50 ppm read 48).
- **The converter length** (#382, owner's ROZHODNUTÉ 17.11.2026: SoundGrid at 96 kHz too, the converter at the minimum): `Spec::converter_taps` (None = 256, as before), 32-256 in steps of 8 (rubato rounds any other length up silently), checked at `Bridge::new` and applied to all three players (the idle from-ASIO one too) via `tapped`. 48 taps at 96<->96: 0.250 ms a direction, flat to 20 kHz; 32: 0.167 ms, -0.40 dB at 20 kHz (issuecomment-6952851834: with a rate change 192 taps keep 20 kHz flat, 128 lose 0.9 dB). `Stats::converter_delay_ns` reads each direction's delay; a test that the length really plays compares the phase of a 100 Hz tone through two players on the same steps (`a_player_with_48_taps_plays_1_083_ms_earlier_than_the_default`: 104.000 frames), since the published delay comes from the same converter it would prove nothing alone.
- **A driver with no clock** (#447): re-opened 4, 8, 16, 32 s after each open, then every 60 s (`state::NO_CLOCK_REOPEN_S`, `no_clock_reopen_ns`; the runner's `clock_reopens` starts again with each wait, reset at the clock, at `wait()` and at any other calm close; a run not yet waiting always starts its wait, the one WARN, before a re-open, so a slow open never skips it). Field basis (dsg, 19.11.2026): SoundGrid opened while its network was down never ticks by itself (53 s with the link back), a re-open brings its clock 10.7 s later (with a `resyncs` rise), another open gave it 2.49 s after the open: so the first re-open is never at the 2 s wait start, and keep a window over ~11 s early in the schedule. The re-open logs at DEBUG only (songplayer#233 issuecomment-6060957003: the owner asked only for no loop or crash and a start by itself; a PC with no PTP leader waits for days); to date one in a field log, read `clock_waits` in dasio's 10 s `bridge counts` lines. dasio's log rotates as `C:\ProgramData\dasio\instance-1\dasio.log.1..3` (10 MB each): a window an hour back is usually in `.1`.
