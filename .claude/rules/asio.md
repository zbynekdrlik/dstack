# The ASIO host (dstack-asio, #243)

- **Lifted from SongPlayer, byte for byte where it writes:** `format::Sample::encode` is SongPlayer's `asio_format` encode on `f64`; `an_f32_widened_to_f64_writes_songplayers_bytes` pins it against SongPlayer's formula written out in the test. Never change the rounding or the full scales: SongPlayer moves onto this crate with no behaviour change.
- **Every decision is pure and Linux-tested; `win.rs` only calls the driver** and is excluded from the mutation gate (`.cargo/mutants.toml`). A new Windows decision goes into `state`, `device`, `engine` or `runner` with a test, never into `win.rs`. Times are ns (SongPlayer's are 100 ns).
- **The buffer switch is `Engine`:** decode the used inputs, run the app's `Process` under `catch_unwind`, encode every driver output (unmapped ones zeroed). It allocates nothing; a panic plays silence from then on and the `Runner` closes the run (`faults > 0`).
- **A process that loads an ASIO driver spawns no child** (SoundGrid resyncs on any spawn from that process, songplayer #233). dasio's instance process must keep to it.
- **Bridge targets** (#247): the ASIO buffer + one pump block by default (256 at 96 kHz: 4.0 ms). The simulated-clock tests pin ±50 ppm at the default, ±100 ppm at a set 5 ms, and at most two dropouts in the first 80 s (at about 27 s and 67 s) then none at ±100 ppm at the default (5 ppm/s slew, 60 s rate lock). Never loosen the asserts to make a default hold more.
- **The bridge simulation tests take ~17 s** (two sinc converters at 96 kHz for 180 s each): a crate test run passes the harness's 180 s background limit only with `timeout 170`; run a throwaway probe of other drifts/targets as its own `cargo test <name>` in the background and wait on its output file (never end the turn while it runs as a subagent).
- **azo 0.4.0 cross-compiles** for `x86_64-pc-windows-gnu` on dev1 (its build script runs windows-bindgen on the host): check `cargo clippy --target x86_64-pc-windows-gnu -p dstack-asio` before a push.
- **The from-ASIO figures** (#325, `bridge/age.rs`): the receiver figure is MEASURED, never modelled. `from_asio_packet_age_us` is the minute's max of `TxShared::take_app_view().age_peak_ns` (a per-lane peak of its own, `age_app_peak_ns`; never take the late watch's `take_age_peak`, it would starve it), and `from_asio_min_receiver_latency_us` = that + `RxShared::network_p99_ns()` or 200 us. The modelled block age (call period + hand-over wait; `compare_exchange(NONE, now)` at the hand-over, `swap` at the pump's take) is a diagnostic only: dasio's field read 1.9 ms modelled vs 1.0-1.4 ms real packet ages (16.11.2026). The hourly WARN comes only from a receiver's own `over_latency` rising (`BlockAge::look`, from the app's status loop, never the pump: the view locks the TX table). The status keys are dasio's (`bridge_json`). Tests drive it with `BlockAge::new(clock)` / `Bridge::with_clock` and a fake clock; a test that checks a warning's text never names a receiver after a word in it ("high" is in "higher", "old" is in the packet-age clause).
- **The to-ASIO side is pulled by the driver's buffer switch** (#307 step 2, `Bridge::pull_to_asio`): the switch `try_lock`s the shared `RxPull` (an `Arc<OnceLock<Mutex<RxPull>>>` the bridge, the pump's side and every driver side hold), pulls, then `serve`s (the rtsan-marked part: from-ASIO feed, age, player). The pump's side feeds the to-ASIO FIFO only unpulled and only for a block with RX inputs (a pulling app's pump has none, so the moments before `pull_to_asio` push no zeros). While no driver is open the app's loop calls `Bridge::keep_pulled` (the idle drain), or the flow reads silent and is closed. Pulled, the to-ASIO player's producer chunk is the ASIO buffer (`to_asio_chunk_ns`). Prove a change with `tests/to_asio_pull.rs` (whole device: 31 pump stalls of 10-20 ms against a steady 256 @ 48 kHz switch, 0 underruns / 0 off; the pump-written path had 13 / 6350), `tests/to_asio_alloc.rs` and the rtsan job's `-p dstack-asio --test rtsan`. A pull unit test sends its packets after the first pull (`Start`): a new flow's first drain drops what waited in its socket as `stray` (#326).
