# RX subscriptions: flows, multicast and our own unicast flow

- **Own unicast over a coarser multicast is opt-in** (#297, v0.6.133): only a device whose config SETS `arc_rx_fpp` (`DeviceConfig::arc_rx_fpp: Option<u16>`, `Manager::own_unicast`) leaves a multicast flow with more frames a packet than its unicast flow would carry. A device on the default must see zero change: the band's FOH/PA feed (a dasio device on the default) takes the same transmitter's multicast flow. A test that needs the opt-in builds its manager with `arc_rx_fpp: Some(4)` (`subscribe/tests/coarse_multicast.rs`); `tests.rs::manager()` is the default device.
- **Owner's rules for that path** (14.11.2026, "extrémne opatrne"): never write to the transmitter's multicast flow; ask only into a free TX slot (`Multicast::free_slots` = the flow list's `slots` less its flows; unknown for an ARC 2.7 list or one with an unread record, and unknown asks nothing); a refusal, no answer or a silent grant keeps the multicast flow with no other side effect (no `failures`, `unanswered` or `last_request` change, no status change); make-before-break.
- **An `upgrade` flow carries no route until it delivers** (`Manager::promote`). Every helper that reads "a flow carries this TX channel" or "a flow nobody routes to" must treat it apart: `carrying()` skips it, `close()` counts it as used while young, `answered`/`give_up` send it to `upgrade_answered`/`upgrade_failed`, and `abandoned` keeps its flag so a late answer to a given-up request counts nothing.
- **Checks that `reresolve` already makes are unreachable later in the same tick**: a changed record or a moved group is unrouted before `upgrade()` runs, so re-checking them there only leaves unkillable mutants.
- **Free-slot order in tests:** a freed flow slot is taken last (`free_slot` picks the slot freed longest ago, never-used first), so after a refusal the multicast flow joins slot 1, not 0: read the slot with `group_slot(&m)`.
- **A new `DeviceConfig` field or type change breaks iemmixer's full struct literal** (`crates/iem-engine/tests/dante_loopback.rs`): name its migration line in the CHANGELOG.
- **Module layout** (#300, v0.6.134): `subscribe.rs` keeps the types and the public lifecycle (new, set, tick, answered, stop_all, status, changed); `publish.rs` the RX thread's plan/route/views, `request.rs` resolving and requesting (`fpp_for` re-exported at `subscribe::fpp_for`), `slots.rs` the flow-slot bookkeeping, `coarse.rs` the opt-in own unicast flow. A helper called from the parent or a sibling is `pub(super)`. The tests read names through `use super::*`, so a name only they use stays a `#[cfg(test)]` import in `subscribe.rs` (RxPlan, RxRoute, Multicast, MulticastLookup); an intra-doc link in the module docs to a type not imported there needs its full path.
- **A flow's latency is the receiver's alone** (#352, v0.6.157): a Dante flow request (`FlowRequest`) carries no latency; a transmitter learns ours by reading our settings (`flows/receivers.rs`). So a device latency write never re-requests a flow: `Manager::set_latency` re-derives every running flow's `latency_ns` with `flow_latency` (its transmitter's advertised latency or ours, the larger), the same rule a new flow gets. Any new place that makes or changes a `Flow` uses `flow_latency`, never its own `max`. A lower write moves the read point; the engine pump re-bootstraps at any moved playout (`Cause::Retime`), so expect one `rebootstraps_retime` per write in a test.
- **A flow's read is logged at its grant** (#403): `RX flow granted device=.. flow=.. latency=.. playout=.. delay=.. advertised=..`, samples at the device's rate, the same figures as the status `rx[]` (`Driver::read_of`: `Manager::flow` + `rx_plan`). `delay` > 0 is a transmitter latency over ours read later in whole blocks, and every app block's `play_at` moves with it (#402: mbc-snv's 40 ms flow read 28 ms later on stream-obs, `delay 2688`, then 0 after dasio went to 5 ms). A grant of a flow no longer in its slot logs `device=-` and no figures. A new field goes after these (consumers grep the line); its test counts the fields in order (`daemon/media/tests/grant_read.rs`).
- **The read point is P - H on a leading device** (#476, `Manager::read_point`, `Manager::handoff_lead`): with the device config's `rx_handoff_lead` (every dlink device with RX, never one that pulls its RX) the pump reads our flows at P - H, H = 30 % of P, and `read_at` delays a flow by its own need (`need`: its transmitter's advertised latency or the `playout_override`, at least its fpp) past that, in whole blocks; without the lead the figures are exactly the old ones (need past P). The plan's `latency` (status `playout`, `late_after`, the intake's late and lost judges) is that read point, never P. A flow read later because of the lead logs `daemon::media::LEAD_READ_LATER` once at its grant. A dlink sender at the receiver's own P is past P - H: read ceil(H / B) * B - H later than before.
