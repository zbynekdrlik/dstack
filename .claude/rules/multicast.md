# Multicast sockets and their group membership

- **A long-lived multicast socket keeps its group only with a watch** (#282). On Windows an address removed and added again (`netsh ... set address`), often with a new interface index, drops the membership; the socket keeps working for unicast, so nothing fails loudly. Every socket that joins once and lives on holds a `membership::Membership` and calls `keep` from its own loop: discovery and the latency listener `rejoin` (leave + join) on the same socket, RX flows are asked from the daemon's tick (`RxShared::rejoin_groups`, never the RX hot path). A socket opened per request (`info::client::group_socket`) needs none. A new long-lived owner must do the same. The one exception is the mDNS daemon's socket (#442, `announce::mdns`): mdns-sd's own IP check keeps it, set to the watches' 2 s (`set_ip_check_interval`; leaves a gone address, joins a re-added or re-indexed one), with the same known limit; the Windows responder no longer joins, its watch only re-opens and announces (`responder::REOPENED`).
- **A long-lived multicast SENDER keeps its interface with the same watch** (#409, stream-snv 18.11.2026: a USB NIC reset re-created `rig0` under a new ifindex, same name and address; the directory found its transmitter never again until OBS restarted). Linux turns `IP_MULTICAST_IF`'s address into the interface INDEX when it is set and routes every later multicast send by it: after a re-create every send fails with ENODEV (`No such device`), logged at debug only, while unicast from the bound address works. Proven in a namespace (`sudo unshare -n` on companion-snv: a dummy `rig0` deleted and re-added, ifindex 2 -> 3, sends fail until the option is set again; dev1 has no sudo and no user namespaces, so no test re-creates an interface). Every socket that sets `IP_MULTICAST_IF` once and lives on names it again after a change: `membership::send_on` (by address, on Windows by index when that fails, through `sendwatch::interface_by_index` as the info server does) from `Membership::keep_as` with `membership::SEND_IF`'s words, so the INFO line says `multicast send interface named again`, never "group re-joined" (the instance queries' thread; Discovery's sweeper beside its listener's rejoin, both tried whatever the other did, `discover::follows` picks the words). Feed each send's result to a `SendWatch` too (`subscribe::instance::Out`: counted in `Instances::send_errors`, one warning a minute, `send_on` after 3 in a row): before #409 a failed query was a debug line, and a socket that sent nothing went unseen for 23 minutes. Its thread takes a `membership::Lister` (pub(crate); the OS's list every 2 s by default), so its wiring is tested with `membership::fake::Fake` (an index the test moves, reads counted): set the option to 0.0.0.0, wait two reads, move the index, read the option back (`socket2::SockRef::multicast_if_v4`) from a `#[cfg(test)]` clone of the thread's socket. A send watch's wiring: queries to 255.255.255.255 (refused without `SO_BROADCAST`, no group, so no list watch) name the interface after 3 failures.
- **Our own multicast TX flows keep their interface from the daemon's tick** (#411): the TX flow sockets (`media/tx/multicast.rs` `multicast_out` at bind) are named again by `TxShared::keep_send_interface` (`send_on` on every socket, `FLOW_SOCKETS` in the line) from `Driver::tick`, with a `Membership` of its own beside the RX groups' (#282), so a failed TX naming never re-asks the RX rejoin and the reverse; both read the `Driver`'s one `Lister` (`Driver::set_lister` in tests). Their failed sends already had the #340 shape (lane `send_errors` + `last_os_error`, `media::late::SendWatch` once a second; ENODEV 19 and ENETUNREACH 101 are not transient refusals, never retried). The wiring test is a tick with a 1 ms fake list, a real 2 ms sleep between ticks (the tick is synchronous, no `until` needed): `daemon/media/tests/send_if.rs`.
- **The whole-device re-create test is CI's `recreate` job** (#411, #414, `tools/linux/tests/recreate.test.sh`, root): two private namespaces joined by a veth pair named `rig0` at both ends (a 10.71.0.1, b 10.71.0.2; deleting one end deletes both), one peer in each, b's TX 1 by a SAVED multicast flow (a `[[multicast]]` in its `--state` file: the only way a peer has our own multicast flow without a controller), a's by unicast. Both run as root, so each opens the AF_PACKET socket and a's unicast flow to b (a neighbour the kernel resolves on a real link) goes past the qdisc: a's TX lanes' `direct` count (`recreate_gate.py direct`) must rise in each window. On ONE dummy interface (#411's first shape) no flow ever went direct: both peers on one address, and a dummy is NOARP (`/proc/net/arp` skips NOARP entries) and drops what it is handed, so a direct frame would never arrive. The pair deleted, 5 s gone, re-added (a's index must change); both must deliver again within 60 s, a's still multicast and a's still direct, b's log must say `the TX flow sockets` and a's `the direct socket sends on the interface's new index`. Its reads are `recreate_gate.py` (unit tests run without root). While the interface is gone the multicast slot fails `os_error=101`, after the re-add `19` until named again; a direct send to the old index fails `6` (ENXIO). Launch a netns process with `ip netns exec "$NS" bin &`, never through a shell function (`in_ns bin &` forks a subshell: `$!` is not the peer, the closing INT never reaches it and the peers outlive the script, holding its stdout).
- **The socket past the qdisc follows the re-created interface's index** (#414, companion-snv netns 18.11.2026: origin/dev's a sent b nothing for 60 s after the re-add, every slot b asked again failed `os_error=6`, while b's multicast to a came back). `media::bypass::Direct` is an unbound AF_PACKET socket (protocol 0) that names the interface in EVERY send (`sll_ifindex`), so only that index goes stale, never the socket: `Direct::ifindex` is an `AtomicI32` the TX thread loads per send (Relaxed, lock-free, no allocation), moved by `Direct::follow(nic)` (`if_nametoindex` by NAME, as `/proc/net/arp` filters by name) from the same TX watch as the flow sockets (`TxShared::keep_send_interface` runs `send_on_again` and `follow_direct` (`media/tx/direct.rs`), both tried whatever the other did). No re-open (the fd serves any interface; a swap would need a grace period for the TX thread's `&Direct`) and no UDP fallback on ENXIO (a second send on the hot path, and the MAC comes back by name anyway). Until the watch's next look (2 s) direct sends fail and are counted, as the multicast flows' ENODEV. Tests: no test has CAP_NET_RAW, so `Direct::stand_in` (cfg(test), a UDP socket's fd, never sent on) + `TxShared::with_direct`/`direct_index` (`media/tx/tests/direct.rs`, through `membership::fake::Fake`); the decisions are `bypass::index_of` and `moved_to`, free functions so `.cargo/mutants.toml`'s `bypass.rs.*Direct::` exclusion does not hide them; `Direct::follow` itself stays excluded as glue, since its off-Linux twin of the same name can never be caught on the Linux gate. Known limit: an address that moves to an interface of ANOTHER name keeps the old name's index (the act fails and warns each look, its error naming `the direct socket (audio TX past the qdisc) on <nic>` under the watch's "multicast send interface not named again" words; its slots get no MAC on the old name, so they go through the UDP sockets).
- **The host frame sender's NIC follows the re-created interface's index** (#417, Windows; found by #414's lane in the code, not reproduced in the field yet). `Media::set_frame_sender` finds our NIC once (`bypass::windows::nic`: the adapter's IPv4 `IfIndex`), and `set_host_macs` keeps only the neighbour rows (`MIB_IPNET_ROW2.InterfaceIndex`) on that index: after a re-create every row was filtered out and the flows went through the UDP sockets until a restart (nothing lost, but the host's kernel send path unused). The TX watch now moves it too (`TxShared::follow_host`, `media/tx/host.rs`), with the index from the watch's OWN list (`Membership::keep_with` gives the act the `Rejoin`): `if_addrs`' Windows index is `ipv4_index()`, the same IPv4 `IfIndex` field, so the decision has no Windows-only read and is tested on Linux. A list entry without an index fails the act (`host::HOST_SENDER` in the error), and the watch asks again. Known limit: an address moved to ANOTHER adapter (a re-configuration, not a re-create; one NIC per production PC, #155) is followed too, while the frames keep the first NIC's source MAC (`Batch.mac`, set when the TX thread starts); and a re-create between `set_frame_sender`'s adapter read and the watch's first look (milliseconds at the start) is learnt by that look with no change, so the host path keeps the stale index until a later change. The no-index case through the watch is tested with `Fake::without_index`. Whether the host's own sender (dasio's NDIS filter) takes frames after the re-create is the host's side: the field proof (disable/enable the NIC on a Windows test PC, mbc; never a production PC from a lane) watches the TX lanes' `direct` count rise again without a restart.
- **Test the comparison, not the OS event:** `Membership::look`/`poll` take fake `Link` lists and times; the wiring of a thread is tested with an injected reader (`responder::Watch::read`). Wait in a test for the watch to have READ the state you set (count the reads), never a fixed sleep: the responder's thread blocks up to 250 ms in its receive between looks.
- **Known limit:** a same-index re-add between two 2 s reads is not seen. Windows lists an address again only once its duplicate-address check is done (`if_addrs` 0.15 filters on `IpDadStatePreferred`).
- **A bit mask built in a fresh accumulator from distinct bits:** sum the bits (`.map(|s| 1u64 << s).sum()`), not `|=`: the `|=` to `^=` mutant gives the same mask and cannot be killed (`media/rx/rejoin.rs`). Merging that mask into another one with `|=` is fine when a test makes the two overlap (a plan change and a rejoin in one pass).
- **A wildcard or group-bound listener and other interfaces' traffic** (#289; since #442 the meter reads the mDNS daemon's socket, which turns it off in `Zeroconf::set_tap`): Linux hands a socket bound to the group address or the wildcard every membership of the HOST (another socket's join on the LAN too) unless `IP_MULTICAST_ALL` is off (`socket2::SockRef::set_multicast_all_v4(false)`, Linux only). Windows delivers by the socket's own membership: a `0.0.0.0:5353` socket joined on the Dante address only heard Dante-subnet sources for 20 s on a two-leg PC (14.11.2026). `discover::group_listener` itself does not turn it off (a Discovery in a process without a device may hear the LAN's mDNS on Linux; a device's reads the daemon's tap, #442).
- **A multicast SEND can fail for hours while unicast works** (#340, dsg 15.-16.11.2026: every info/heartbeat send WSAEADDRNOTAVAIL 10049 for ~24 h after a reboot; a new socket did not clear it, an adapter restart did; cause inside Windows unproven). A long-lived sender never logs per packet: it feeds each result to a pure watch (`info::sendwatch::SendWatch`: at most one line a minute with the count, even when failures and sends alternate; reapply `IP_MULTICAST_IF` after 3 in a row, reopen after 10, each kind at most once a period that doubles per reopen up to an hour; a reopen frees the share port with the info port so a member that takes it can serve) and counts it in the status (`info_send_errors`, `info_send_recoveries`). `IP_MULTICAST_IF` by interface index on Windows is the address `0.0.0.<index>` (`sendwatch::index_form`). Test the wiring with an injected `AsyncFn` send that fails with `io::Error::from_raw_os_error(10049)` (`info/tests/send_failures.rs`); on Linux a real send to 255.255.255.255 without `SO_BROADCAST` fails every time (EACCES; WSAEACCES 10013 on Windows). A port taken during a reopen is simulated with `SO_REUSEPORT` on both sockets (unix only): the plain rebind is refused. The wiring tests serve on 127.0.34.1 and .2 (their 8700 and share ports 19213/19214 must be free on the box).
- **One mDNS socket a process and address** (#442, dasio#190: a Windows device process received every mDNS datagram on three joined 5353 sockets, 0.1-0.8 ms of receive DPC each on dsg). Never open another 5353 socket that joins the group in a device process: read the daemon's through `announce::mdns::Mdns::listen` (`Heard::All` or `Heard::Queries`; bounded channels, a full one drops and counts). Windows delivers no multicast to a 5353 socket that has not joined (mbc, 20 s on the Dante leg: joined 185, bound to the address unjoined 0, wildcard unjoined 0), and that socket still sends from its bound address: the responder's answers keep the device's source. Count a process's 5353 sockets on Linux with `/proc/self/fd` inodes matched in `/proc/net/udp` (`tests/mdns_one_socket.rs`), after the daemon answered once (it opens its socket on its own thread) and polled briefly after a stop (it confirms the shutdown before its socket closes). A device's `traffic::neighbours` Discovery (started while its NIC is loud, #203) reads the tap too (`Mdns::listen_on`: the running daemon's, never opened; `Discovery::start_heard`), drained as its socket was (`discover::drain_tap`) and never rejoined (its watch then names only the sweeper's interface); a Discovery in a process with no device (dtray, a controller) keeps its own `group_listener`. `tests/mdns_one_socket.rs::a_loud_nic_s_neighbours_discovery_keeps_the_one_socket` held 2 sockets before (the daemon's and 224.0.0.251's).
- **Linux delivers no multicast to a socket bound to a unicast address, joined or not** (#444, dev1 loopback 19.11.2026: bound to `127.0.0.1:P` and joined, 0 of 5 group datagrams and the unicast one; a wildcard socket on the same port all 5). Windows does (mbc, #442: 185). So an mDNS socket that must hear the group stays on the wildcard on Linux. The #444 trial switch (`mdns_bind_address`, off by default) binds the daemon to the device's address (`Mdns::shared_bound`, vendor `new_tapped_on`) and drops the Windows responder (`Mdns::own_responder_needed`); on Linux it warns at start (`announce::mdns::GROUP_TO_BOUND_SOCKET`, `bound_note`). A unicast to `<address>:5353` goes to the most specific bind on both OSes, so a bound daemon and the responder must never both hold `<address>:5353`. Its tests query `<address>:5353` directly (`Instances::start_to`), and the whole-device test reads `0100007F` in `/proc/net/udp`.
