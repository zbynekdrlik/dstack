# Multicast sockets and their group membership

- **A long-lived multicast socket keeps its group only with a watch** (#282). On Windows an address removed and added again (`netsh ... set address`), often with a new interface index, drops the membership; the socket keeps working for unicast, so nothing fails loudly. Every socket that joins once and lives on holds a `membership::Membership` and calls `keep` from its own loop: the responder reopens its socket and announces, discovery and the latency listener `rejoin` (leave + join) on the same socket, RX flows are asked from the daemon's tick (`RxShared::rejoin_groups`, never the RX hot path). A socket opened per request (`info::client::group_socket`) needs none. A new long-lived owner must do the same.
- **A long-lived multicast SENDER keeps its interface with the same watch** (#409, stream-snv 18.11.2026: a USB NIC reset re-created `rig0` under a new ifindex, same name and address; the directory found its transmitter never again until OBS restarted). Linux turns `IP_MULTICAST_IF`'s address into the interface INDEX when it is set and routes every later multicast send by it: after a re-create every send fails with ENODEV (`No such device`), logged at debug only, while unicast from the bound address works. Proven in a namespace (`sudo unshare -n` on companion-snv: a dummy `rig0` deleted and re-added, ifindex 2 -> 3, sends fail until the option is set again; dev1 has no sudo and no user namespaces, so no test re-creates an interface). Every socket that sets `IP_MULTICAST_IF` once and lives on names it again after a change: `membership::send_on` (by address, on Windows by index when that fails, through `sendwatch::interface_by_index` as the info server does) from `Membership::keep_as` with `membership::SEND_IF`'s words, so the INFO line says `multicast send interface named again`, never "group re-joined" (the instance queries' thread; Discovery's sweeper beside its listener's rejoin, both tried whatever the other did, `discover::follows` picks the words). Feed each send's result to a `SendWatch` too (`subscribe::instance::Out`: counted in `Instances::send_errors`, one warning a minute, `send_on` after 3 in a row): before #409 a failed query was a debug line, and a socket that sent nothing went unseen for 23 minutes. Its thread takes a `membership::Lister` (pub(crate); the OS's list every 2 s by default), so its wiring is tested with `membership::fake::Fake` (an index the test moves, reads counted): set the option to 0.0.0.0, wait two reads, move the index, read the option back (`socket2::SockRef::multicast_if_v4`) from a `#[cfg(test)]` clone of the thread's socket. A send watch's wiring: queries to 255.255.255.255 (refused without `SO_BROADCAST`, no group, so no list watch) name the interface after 3 failures.
- **Our own multicast TX flows keep their interface from the daemon's tick** (#411): the TX flow sockets (`media/tx/multicast.rs` `multicast_out` at bind) are named again by `TxShared::keep_send_interface` (`send_on` on every socket, `FLOW_SOCKETS` in the line) from `Driver::tick`, with a `Membership` of its own beside the RX groups' (#282), so a failed TX naming never re-asks the RX rejoin and the reverse; both read the `Driver`'s one `Lister` (`Driver::set_lister` in tests). Their failed sends already had the #340 shape (lane `send_errors` + `last_os_error`, `media::late::SendWatch` once a second; ENODEV 19 and ENETUNREACH 101 are not transient refusals, never retried). The wiring test is a tick with a 1 ms fake list, a real 2 ms sleep between ticks (the tick is synchronous, no `until` needed): `daemon/media/tests/send_if.rs`.
- **The whole-device re-create test is CI's `recreate` job** (#411, `tools/linux/tests/recreate.test.sh`, root, a private netns): two peers on a dummy `rig0`, b's TX 1 by a SAVED multicast flow (a `[[multicast]]` in its `--state` file: the only way a peer has our own multicast flow without a controller), a's by unicast; `rig0` deleted, 5 s gone, re-added (index must change); both must deliver again within 60 s, a's still multicast, and b's log must say `the TX flow sockets`. Its reads are `recreate_gate.py` (unit tests run without root). While the interface is gone the multicast slot fails `os_error=101`, after the re-add `19` until named again. Launch a netns process with `ip netns exec "$NS" bin &`, never through a shell function (`in_ns bin &` forks a subshell: `$!` is not the peer, the closing INT never reaches it and the peers outlive the script, holding its stdout).
- **Not covered yet (#414):** the Linux AF_PACKET bypass socket (`media::bypass::Direct`) keeps the interface index it opened with (`sll_ifindex`), so unicast flows to resolved neighbours after a re-create likely keep failing (read in the code, not reproduced; #411's lane return hands it to the main session as a follow-up candidate); the test's flows never take it (both peers on one address: no resolved neighbour).
- **Test the comparison, not the OS event:** `Membership::look`/`poll` take fake `Link` lists and times; the wiring of a thread is tested with an injected reader (`responder::Watch::read`). Wait in a test for the watch to have READ the state you set (count the reads), never a fixed sleep: the responder's thread blocks up to 250 ms in its receive between looks.
- **Known limit:** a same-index re-add between two 2 s reads is not seen. Windows lists an address again only once its duplicate-address check is done (`if_addrs` 0.15 filters on `IpDadStatePreferred`).
- **A bit mask built in a fresh accumulator from distinct bits:** sum the bits (`.map(|s| 1u64 << s).sum()`), not `|=`: the `|=` to `^=` mutant gives the same mask and cannot be killed (`media/rx/rejoin.rs`). Merging that mask into another one with `|=` is fine when a test makes the two overlap (a plan change and a rejoin in one pass).
- **A wildcard or group-bound listener and other interfaces' traffic** (#289, `discover::senders::Meter`): Linux hands a socket bound to the group address every membership of the HOST (another socket's join on the LAN too) unless `IP_MULTICAST_ALL` is off (`socket2::SockRef::set_multicast_all_v4(false)`, Linux only). Windows delivers by the socket's own membership: a `0.0.0.0:5353` socket joined on the Dante address only heard Dante-subnet sources for 20 s on a two-leg PC (14.11.2026). `discover::group_listener` itself does not turn it off (a Discovery may hear the LAN's mDNS on Linux).
- **A multicast SEND can fail for hours while unicast works** (#340, dsg 15.-16.11.2026: every info/heartbeat send WSAEADDRNOTAVAIL 10049 for ~24 h after a reboot; a new socket did not clear it, an adapter restart did; cause inside Windows unproven). A long-lived sender never logs per packet: it feeds each result to a pure watch (`info::sendwatch::SendWatch`: at most one line a minute with the count, even when failures and sends alternate; reapply `IP_MULTICAST_IF` after 3 in a row, reopen after 10, each kind at most once a period that doubles per reopen up to an hour; a reopen frees the share port with the info port so a member that takes it can serve) and counts it in the status (`info_send_errors`, `info_send_recoveries`). `IP_MULTICAST_IF` by interface index on Windows is the address `0.0.0.<index>` (`sendwatch::index_form`). Test the wiring with an injected `AsyncFn` send that fails with `io::Error::from_raw_os_error(10049)` (`info/tests/send_failures.rs`); on Linux a real send to 255.255.255.255 without `SO_BROADCAST` fails every time (EACCES; WSAEACCES 10013 on Windows). A port taken during a reopen is simulated with `SO_REUSEPORT` on both sockets (unix only): the plain rebind is refused. The wiring tests serve on 127.0.34.1 and .2 (their 8700 and share ports 19213/19214 must be free on the box).
