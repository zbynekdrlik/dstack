# Tests in dstack

- **Whole-device tests** (`tests/system_clock.rs`): the host refuses loopback (no MAC, unreachable for Dante), so run the device on the box's routed IPv4 (`UdpSocket::connect` to 192.0.2.1:9, then `local_addr`; sends nothing). Each test binds the Dante ports on that address: take the file's `ONE_DEVICE` lock.
- **Shared dev box:** dcontroller (another account on dev1) runs `dstack-dev` in its own E2E on the same routed address and Dante ports. A whole-device test that fails at once on its start (bind) while one of theirs runs is that collision. Rerun it alone and check `ps -eo user,args | grep dstack-dev` before calling it ours (1.11.2026: `tests/embed.rs` failed once in 0.01 s, passed 7 times after).
- **Parallel worktrees on dev1:** `ONE_DEVICE` serializes whole-device tests inside one process only. Another autopilot lane's whole-device run (another `.claude/worktrees/agent-*` running `system_clock`, `link` or `embed`) binds the same routed address and ports: every test then fails at once at bind (0.07 s), or a later one misses its goodbye or stop. Before calling a failure ours, check `pgrep -af 'deps/system_clock-|deps/link-|deps/embed-'` and rerun when it is empty (#187, 11.11.2026). Even alone, `discovery_lists_our_running_device_and_its_withdrawal` (withdrawal not seen) failed 7 runs in 20 on a loaded dev1 up to v0.6.92: discovery read the busy LAN mDNS group slower than it came and the kernel dropped the goodbye (#206, fixed: `discover::drain`). A "stop not Done" of `two_devices_share_one_address_each_on_its_own_ports` did not reproduce in 40 runs under load alone.
- **Timing on CI and dev boxes:** a normal-priority TX thread wakes over 1 ms late now and then; at the test config's 1 ms latency that restarts the TX schedule (a 2 to 5 ms RX dropout). Whole-path tests use a 10 ms latency, take their counts after the start (0.1 s of RX read), and require no restart and every packet within the latency; real-time lateness is the hardware gate's, never a shared runner's.
- **Docs before a push:** CI's fmt job runs `RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps --locked`. A public item's doc that links a private one (`[`wants_mmcss`]`) fails it, while clippy and the tests pass (v0.6.57 took a second CI round). Run it locally.
- **Check the Windows build before a push:** `cargo clippy --target x86_64-pc-windows-gnu --workspace --all-targets --locked -- -D warnings` (the target is on dev1 since 2.11.2026). An unused import under `cfg(unix)` costs a 20-minute CI round otherwise (0.4.34 took three).
- **Windows CI runs every test:** paths must be absolute on Windows too (`std::env::temp_dir()`), not `/run/...`.
- **Async inputs:** the directory's ARC and DBC records come from direct mDNS queries (no browse since v0.6.56, #141), taken into the book at each lookup of that device. A test answers them with our own responder's `announce::responder::answers` on loopback (`directory/tests.rs::responder`) and waits for `records().arc_at(..)` before the lookup it counts. A channel's own query keeps it from the ARC for `instance::GRACE_NS`: drive the time with `Instances::with_clock` rather than wait 8 s. A daemon test whose lookups must reach the network serves on `NetInfo { ip: LOCALHOST, .. }` with `Multicast::mdns` at a loopback `Responder`; the tests' 10.0.0.10 cannot bind, which leaves both query threads unstarted (a warning).
- **Mutation gate:** per mutant only the unit tests and `tests/hot_path.rs` run (`.cargo/mutants.toml`); a whole-device test cannot run per mutant (ports). A test bound inside a step must carry the step's own time (`Instant` around `step`), not a fixed bound. Host glue that only calls `daemon::serve` (`host::serve_device`) is covered by the whole-device test alone: any edit inside it, a comment too, puts its `Ok(())` mutant in the diff and fails the gate. Leave such functions out of cosmetic changes.
- **Fake time vs real time:** TX lateness adds real time inside a step to the fake PTP time; bound it by the measured step duration.
- **Captured logs:** a test that captures logs with `tracing::subscriber::with_default` calls `crate::test_log::undecided()` first. Without it, tracing's callsite interest cache can keep "never" for a callsite another test thread hit first, and the capture comes back empty about 1 run in 4.
- **Equivalent mutants:** combine disjoint bit fields with `from_be_bytes`, not `(a << 16) | b`. cargo-mutants turns `|` into `^`, which gives the same value, so the mutant cannot be killed. Likewise `2 * X` with a constant X = 2 equals `2 + X`: write sums (`X + S + X`), not the product (dtray's icon, v0.6.15).
- **Inside a `.claude/worktrees/` worktree** `cargo fmt --all` fails: `vendor/mdns-sd` resolves the main checkout's workspace. Check with `rustfmt --check --edition 2024` on each crate root (`crates/*/src/lib.rs`, `main.rs`, Windows-only module files) instead; it follows the `mod` tree.
- **A local test device for a reader (dtray):** `dstack-dev --config <cfg> --ip <routed IPv4> --clock system --control <short path>`, stopped with `kill -INT`. The control socket path must fit SUN_LEN (about 107 bytes): a scratchpad path is too long, so use a short `/tmp/<dir>/c.sock`.
- **dtray's expected devices in a check:** `DSTACK_DEVICES_DIR=/tmp/<dir>/devices dtray --print` reads that folder instead of `/etc/dstack/devices`; an empty `<name>.device` there with no running device prints "<name>: expected, not running".
- **A warn-once flag** (`!flag.swap(true)`): the test makes at least three refusals and counts one warning. With two, the `delete !` mutant (warn from the second on) also warns once and survives (v0.6.18, `Media::app_status`). A warning that depends on an error kind goes in a pure function returning the text (`expected::unreadable`): two arms that both return empty leave the guard's mutants unkillable otherwise.
- **Warnings from a background thread:** `capture_warnings` sees only its own thread's events. A warn-once raised on a worker thread (the app hook's `dstack-app-status`) cannot be counted, and its guard's mutants survive. Let the thread mark the state and warn on the reader's thread (`AppHook::read`, v0.6.19).
- **dtray's Linux tray on dev1:** building it needs `libgtk-3-dev` and `libayatana-appindicator3-dev` (installed on dev1; CI's apt step). With no display, `env -u DISPLAY -u WAYLAND_DISPLAY dtray` must exit 1 at once ("no desktop ... (GTK)"). To check that it runs, use `xvfb-run -a dbus-run-session -- ...` with a temporary `XDG_RUNTIME_DIR` (mode 700). The first instance keeps running and a second start exits 0. `--autostart on` with a temporary `XDG_CONFIG_HOME` writes an entry; check it with `desktop-file-validate`. Wayland's clipboard is not checked this way.
- **Windows GUI checks from dev1:** the Windows boxes on MCP cannot fetch a file from dev1. There is no route to dev1's addresses, the public drop is behind Cloudflare Access, and no box has Rust. Pushing a 6 MB binary through `FileUpload` would mean base64 in the context, which is not workable. A Windows desktop check needs a CI artifact or another transfer path first. A released binary works: `Invoke-WebRequest https://github.com/zbynekdrlik/dstack/releases/download/<tag>/<bin>-<tag>-windows-x86_64.exe` on the box (MCP `Shell`), check its `.sha256`, run it with `Start-Process ... -PassThru -WindowStyle Hidden` and `--state` in `$env:TEMP`, read `<state>.log`, stop it by pid (dsend v0.6.75/76 on resolume-snv, 10.11.2026).
- **Live tests on dev1's Dante NIC** (`dante-net`; the address is in the private config): run the device with `--ip <that address>` and a private config, write its pid to a file, and stop it with `kill -INT <pid>`, which sends the goodbyes. Never use `pkill -f <pattern>`: it also matches the shell running the command and kills it. The ctl `status` request counts show which ARC and 8700 opcodes Dante Controller sends; the once-a-minute "not answered" warning lists the gaps.
- **Unreachable guards:** a run-time check that can never be false, given what the code before it already limits, is a mutant no test can kill. Prove the bound once with `const _: () = assert!(...)` and drop the check (example: the fpp step in `subscribe.rs`: 9 + 8 * 4 * 32 <= 1472).
- **Windows-only code and the gate:** the mutation gate runs on Linux, so mutants in `cfg(windows)` code can never be caught. `clock/sys_windows.rs` is excluded in `.cargo/mutants.toml`. Keep Windows logic that matters in cross-platform functions with tests (e.g. `clock::wait_mode_for`, `clock::realtime_for`), and leave the `cfg(windows)` part as thin glue. A cross-platform hook that only Windows code reads (v0.6.35: `clock::set_pinned`/`pinned`, `RePin::keep`'s mark) still needs a Linux test of its own; the Windows test that proves the behaviour never runs in the gate (PR #128 missed 4 mutants that way).
- **Latency verdict = a real receiver's records, never our counters** (owner, 31.10.2026). Dante heartbeats (224.0.0.233:8708) carry per RX flow slot: record 0x8003 = that second's peak lateness in samples, 0x8004 = cumulative late count (header: count, 0, offset of the values). Map slot to transmitter with ARC 0x3000 + 0x3200 (page body `0,1,start,0,0`). Probe: `~/.claude/work-products/dstack/rxlat.py <our ip> <receiver ip> <s>` (exit 1 on late or peak over latency). Every gen3 fault tonight (deep C-states, TX/RX same FIFO priority on one core, fq_codel qdisc) was invisible to our counters; checklist in `docs/linux-box.md`; Windows (FOH PC, 1.11: spinning threads on the NIC's RSS CPUs, a NIC shared with bulk TCP) in `docs/windows-box.md`.
- **The IEM card is shared with iemmixer's box:** use only card RX 104/105, tell iemmixer before subscribing, unsubscribe and stop the dev1 device after; a second sender on the card spoils its measurements.
- **Constant bounds:** clippy refuses `assert!` on constants inside a test; put `const _: () = assert!(...)` next to the constant.
- **Windows runners refuse some high ports** (excluded port ranges, WSAEACCES 10013): a test never binds a fixed port near 65535 and never relies on binding in order to reach a range check (v0.4.39: the RX port-base test failed on 65531). Pure range logic gets a pure function and a boundary test.
- **Probing hardware on 8700:** a device answers on the info group 224.0.0.231:8702, from its own port, with its own sequence number (not the request's). Match a reply by source address and reply opcode, never by seq. Dante Controller caches a device's answers: to capture its full read sequence, restart DC under the capture (pktmon on mbc, filtered by control ports, without the 614xx audio range).
- **Socket loops and the gate:** put each read's decision (hand on, go on after a timeout, end on an error) in a pure function that takes the `io::Result`, and unit test every arm (`latency::hand_on`). On dev1 other devices' heartbeats fill every gap, so a test cannot count on a read timing out on a real group socket. A loop over several sockets with read timeouts drains each one while it has datagrams (`discover::drain`): one read per socket a pass waits the idle socket's timeout every pass, and a busy group (dev1's LAN mDNS: about 30 datagrams/s) then overflows its queue and the kernel drops datagrams (#206: 189 KB queued, up to 73 drops a run). Check a suspect socket's `/proc/net/udp` queue and drops column while the test runs.
- **Load reproductions on dev1:** no stress-ng; `(while :; do :; done) &` per busy loop (24 = load ~28, 64 = load ~80). A loop script whose own arguments name `deps/system_clock-...` matches the parallel-lane `pgrep -f` check itself and waits forever: anchor it (`pgrep -f '^[^ ]*deps/(system_clock|link|embed)-'`) and run a copy of the test binary named `.../deps/system_clock-<x>`, so other lanes' checks still see it and a rebuild does not swap it mid-loop.
- **A consumer reports silence:** first read its device from dev1's Dante NIC, read-only. Find its ARC port with `avahi-browse -t -r -p _netaudio-arc._udp`. The 0x3000 page gives each RX channel's TX channel and device, and its status word at bytes 12-15 of the entry (`subscribe/sub_status.rs`). The heartbeat's 0x8003 record gives the device's rate. 3.11.2026: the intercom read 21 on all four channels, from a 48 kHz device on a 96 kHz network.
- **Filters in whole-device tests:** a FIR rings on a step from silence (about 7 % over for the 2:1 half-band). Assert the settled level (the last sample), never the peak.
- **A receiver's flow request fails (status 21 at the receiver):** capture its request at the receiver with pktmon (mbc: `pktmon filter add -i <tx ip> -t UDP -p <flows port>`, then `etl2txt -v 3 -x`). Parse the payload with `dstack::flows::control::parse_request` in a throwaway example. Our answer's status is in the reply (0x0302 and so on). 3.11.2026: DVS asked fpp 60 whatever we advertised. Prove a cause before shipping a fix for it: the missing `_netaudio-dbc` looked like a cause the same night, and was not.
- **A gate chain that greps its own output never stops:** `cargo clippy … | grep …; git commit` commits even when clippy failed (the pipe's status is grep's). Read the output before the commit, or commit in a separate call. 3.11.2026: a commit missed a Windows caller this way, and the next commit fixed it.
- **The local mutation gate** is cargo-mutants 27.1.0 (as CI) since 3.11.2026. Run it as CI does: `NEXTEST_PROFILE=mutants cargo mutants --in-diff <diff> --baseline=skip --timeout 60 -j 4 --test-workspace=true`. The diff is CI's too: `git diff origin/main -- '*.rs'` (the PR's whole diff, `.rs` only), plus CI's `--package dstack --package dstack-audio-io --package dlink --package dstack-resample --package dtray --package dlisten --package dstack-endpoint --package dsend`. A diff against `origin/dev` holding only the newest commits ran clean locally on #148, and CI then found 4 survivors in older commits of the same PR (v0.6.54). Without `--baseline=skip` the baseline runs `cargo test -p <crate> --test hot_path` and fails for a diff in dlink or dstack-resample alone (3.11.2026).
- **Thread stress tests on runners:** a spawned thread can start tens of ms late on a runner, which never happens on dev1. Before calling a stress-test fix done, reproduce the runner's order locally with a temporary `sleep(50 ms)` at the thread's start (v0.6.8: the ring's reader started late; with no read yet `write_at` has no early check, and the test failed twice on CI after passing 15/15 locally). Prime the shared state the check needs (`read_at` before the writer) instead of loosening the invariant.
- **Exclusion patterns match prefixes:** `.cargo/mutants.toml`'s `exclude_re` entries are regexes over the mutant's name (`tx.rs.*send_one`), so a new function named `send_one_retrying` would be excluded silently and its mutants never tested. Name a new tested helper so no exclusion matches it (v0.6.21: `send_with_retries`).
- **A wait loop with a comparison** (`while start.elapsed() < d`) leaves the `<` to `<=` mutant, which waits the same and cannot be killed. Write it without a comparison: `while !d.saturating_sub(start.elapsed()).is_zero()`, and test that it waits at least `d` (v0.6.21, `media::tx::spin_for`).
- **Retry loops in the TX pass:** keep the loop generic over closures (`send`, `age`, `wait`; `media::tx::send_with_retries`) so a unit test drives it with a fake send that fails with given OS codes; the real socket never refuses on demand. Generic closures keep the hot path allocation-free.
- **dlink's pump block is 128 frames by default** (v0.6.20, #90), not the stack's `stream::BLOCK` 32. Its whole-device expectations follow it: `pump.offset` = B + P + W (848 at 48 kHz, 1507 for a 48 kHz app on a 96 kHz device at the 15 ms default since v0.6.28; the tests derive them from `Config::split`), and a 48 kHz app on a 96 kHz device gets 64 frames a block. A dlink test about something else that needs 32-frame blocks sets `.block(32)`. W is 2/5 of the budget (`dlink::work_margin`, 6 ms at the default 15 ms, 4 ms at 10 ms; v0.6.24, #1), at least the block and 2 ms; on a device with TX it gives way to P's TX floor when the budget leaves no room for both, at 10 ms for example (`dlink::tx_floor_ns`: 32 frames + 0.25 ms + 4 ms, 4.58 ms at 96 kHz, 4.92 ms at 48 kHz; v0.6.28, #1), e.g. W 223 for a 44.1 kHz app on a 96 kHz device (the sinc); a 48 kHz app there converts through the half-band (0.64 ms) and keeps W 384. An RX-only device's W is the whole budget (`dlink::rx_work_margin`: 1440 at 96 kHz, 720 at 48 kHz at the 15 ms default, at most `stream::MAX_WORK_MARGIN`; v0.6.32, #1), since W is in none of its paths, so an RX-only test config's `pump.offset` is B + P + the budget; its P and RX path are as with a 6 ms W. A config whose TX path cannot hold the TX floor is refused: a test at block 256 on a 48 or 44.1 kHz device, or 48/44.1 at block 128, needs a larger budget (12 ms) or a smaller block; at the default 15 ms every pair fits. Unit tests pin the 10 ms numbers with the tests' `TEN_MS` (an app may still set it) and the default's in `the_default_15_ms_fits_every_common_config_with_w_6_ms`. P is not set but split from the budget (15 ms by default since v0.6.28, 10 ms before; `dlink::split`, v0.6.22, #68): a test pins a P only from `split`'s numbers, and the loop test (`tests/link.rs`) checks them against a step sent through our own flow. P follows the directions the device has (v0.6.24, #1): a config with RX channels only (or TX only) splits by that direction's work alone, so a one-direction test config gets a larger P than the same rates with both; `Config::split` gives the number to pin.
- **A late pump in a whole-device test** (v0.6.24, #1): a processor that sleeps (`Napping` in `crates/dlink/tests/link.rs`) makes the pump late on demand; a pump more than W behind a block restarts (`rebootstraps` in the pump view) and its blocks are lost. Leave the nap several ms under W + B: at a 10 ms budget W is 4 ms and wake jitter on dev1 (load 12) took the 1.3 ms of slack a 4 ms nap left, so that test runs at a 20 ms budget (W 8 ms). The default budget's tolerance is checked on the pump's schedule itself (`dstack::stream::Blocks` at `Timing::of` the split's device config; a dlink unit test), which needs no clock or threads.
- **The host frame sender's TX path on Linux tests** (v0.6.22, #1): `TxShared::use_frame_sender` + `set_neighbours` drive the Windows host path on any OS (`Media::set_frame_sender` is the Windows-only setter). Set the neighbours AFTER the flows exist: the MAC words follow the table's plans at that moment, and production refreshes them each second. Call `use_frame_sender` before `Transmitter::new`; after it the sender is refused. A loopback receiver's buffer holds about 270 small datagrams, so a test that sends hundreds through the UDP fallback counts the lane's `packets`/`send_errors`, not what the socket still holds. Distinct receivers by IP use 127.0.0.2 (the neighbour table is keyed by IP).
- **A cfg(windows) branch inside a cross-platform function** leaves mutants the Linux gate can never kill (and the other arm's constant is often equivalent): keep the function thin and list it in `.cargo/mutants.toml` with the reason (v0.6.22: `Media::set_frame_sender`), with its decisions tested elsewhere.
- **TX lateness needs a known receiver latency** (v0.6.23, #1): `over_latency` and the late watch count only against the latency the receiver states (ARC 0x1100, `flows::receivers`), never while it is unknown. A TX test that expects late packets sets it after the flow exists: `rig.shared.set_receiver_latency(slot, v4(&rig.rx), ns)`; the value is keyed by destination, so a slot sending elsewhere reads 0. A whole-device test reaches it through our own device's ARC record within a few seconds (`receiver_latency_us` in the status), so poll for it with a bound rather than reading once.
- **Info lines in a test:** `crate::test_log::capture_at(Level::INFO, f)` captures any level (`capture_warnings` is its WARN form). A condition that only decides whether to log (a value changed) is a mutant until a test counts the line.
- **A watch on the daemon's tick** (v0.6.25, #1: `stream::watch::PumpWatch`): the pure `look` gets fake times, but the wiring needs a test through `Driver::tick` (`daemon/media/tests.rs`, `the_driver_s_tick_warns_once_...`): tick once to learn, change the counts, sleep a real 1.01 s (`rx.now_ns` is monotonic, not the media clock), tick again inside `capture_warnings`. The tick runs on the test's thread, so the capture sees it. In a watch test, any `PumpStats::record` longer than the block's period (0.67 ms for block 64 at 96 kHz) is an overrun, which the watch reports: a "quiet second" needs blocks under the period (v0.6.32, the per-second `max_process_us` test).
- **Debug builds and the converter:** an unoptimised rubato overruns every pump block of a converting device (intercom 4.11: 2.84 ms against a 1.33 ms block). Our workspace sets rubato and dstack-resample to opt-level 3 in every profile; a consumer must set it in its own workspace (Cargo reads profiles from the top workspace only; dlink's crate docs say so).
- **Filter quality numbers are measured, never assumed** (v0.6.28, #1): a doc or CHANGELOG figure for a converter (ripple, stopband, THD+N, folded/image level) comes from a throwaway test that prints it through the crate's own helpers (`tone`, `thd_n_db`, `level_dbfs`, `run_fixed_input` in `dstack-resample/src/tests.rs`), removed before the commit; the committed test asserts a bound under it. The half-band's 28 kHz image measured -150.2 dBFS where the design text said -150.6.
- **Same-name cfg variants and the gate** (v0.6.28, #1): cargo-mutants mutates a `cfg(windows)` function too, under the same name as its Linux twin (`pin_to_cpu`), so no `exclude_re` can single out the Windows body. Put a new Windows decision in a pure cross-platform function (`media::repin::outcome`), give the Windows glue a name of its own if it must be excluded, and leave such twins' Windows bodies out of edits. Run the full suite with `--no-fail-fast`: `cargo test` stops at the first failing binary, so a port collision in one hides the rest.
- **Samples from a latency:** `dstack::clock::latency_samples` rounds to the nearest sample (8364583 ns at 96 kHz is 803, not 802). Derive a pinned P in samples with it, or from `Config::split` in the test, never with a truncating `ns * rate / 1e9` print (v0.6.28: a pinned 802 failed against the running device).
- **Arithmetic on two real clocks' reads** (v0.6.31, #1, `clock::linked::offset_of`): a test that controls the gap between reads with a spin or sleep against a real `MonoClock` kills a mutant only when the box is idle; under the gate's `-j 4` the gap grows and the mutant survives. Put the arithmetic in a pure function of the read values and pin it with numbers; keep the live test for the wiring only.
- **The local mutation gate past 3 minutes** is moved to the background by the harness: read its output file when it ends, never start a second copy meanwhile. A dispatched worker (a subagent) must not background it: start it detached (`setsid nohup cargo mutants ... > <log> 2>&1 < /dev/null &`) and wait in ONE Bash call (timeout 600000) with a loop bounded on `$SECONDS < 580` that ends when `pgrep -f 'cargo-mutants mutants'` finds nothing. About 100 mutants take 9-10 minutes on dev1 (#203); a second poll loop of the same shape is hook-blocked.
- **A daemon tick test on 127.0.0.1** (#203): loopback has no NIC sent-bytes counter on every OS (Windows CI runs the test too), so a test that needs the traffic watch to look sets `Driver::set_nic(|_| Some(0))`. A helper thread that serves the test hands its result back over a channel read with `recv_timeout`, never `join`: a regression that never connects then fails in seconds instead of hanging the job.
- **A Windows scheduling regression test** (v0.6.34/35, #1): pin the test thread and a busy lower-priority thread to CPU 0 with `SetThreadAffinityMask`, raise the test thread to TIME_CRITICAL, and assert on the median lateness or on the busy thread's progress. A yield gives the busy thread its whole slice (median 2.49 ms late on windows-2025), and a pure spin starves it (0 progress). Both are deterministic on the runner. Prove RED by pushing the test commit alone to dev and reading the windows job's log.
- **A decision in a thread loop that only Windows takes** (v0.6.38, #1: the TX `run` loop's bounded-escape ask/presend/defer): on Linux the branch never runs, so its `!`/`&&` mutants survive (the gate missed `delete !` in `run`). Put the chain in a `Transmitter` method that takes the clock read and the OS calls as closures (`Transmitter::before_wait`), test it with fake closures (a panicking `defer` proves it is not called), and leave `run` as wiring. A per-thread OS hook with a Linux twin (`clock::ask_escape`/`defer_escape` in `sys_linux.rs` returning false) gets a Linux test that the twin says no, which kills its `-> true` mutant.
- **A receiver reads our flow late while an Audinate sender reads fine:** first swap the sender, not the theory. Subscribe one of the receiver's channels (owner approval) to a dev1 test device whose TX is patched in one way, keep the other channel on the suspect flow, and read both from dcontroller over the same minutes. dstack #141: the UDP checksum (Audinate sends 0, ID 0, TTL 32) looked like the cause in a pktmon diff and was not. The cause was packets sent before their media time (the escape's presend); an UltimoX2 reads an early packet as latency + the early time. An early-send experiment must shift the TX loop's whole clock (step, escape and sleep), or the schedule restarts every pass.
- **A field bug's fix commit says `Refs #N`, not `Closes #N`,** while a field check is still to come: the merge to main closes the issue (dstack #141 had to be reopened).
- **A behaviour that only one OS has** (v0.6.54, #148: Windows binds a multicast socket to the port only, so two groups on one port mix) goes into a field or constant the logic reads (`Manager::port_only`, `media::rx::GROUP_BOUND_TO_PORT`), set from `cfg!` once. A test then sets it both ways on Linux. Written as `cfg!(not(target_os = "linux")) && …` inside the decision, its mutants survive the Linux gate.
- **Windows-only binary glue and the coverage floor** (v0.6.75, #164): CI's coverage job runs on Linux, so glue that can never run there (dsend's loopback capture, session and run loop) counted 360 uncovered lines and failed the 92 % floor. Build such glue `cfg(windows)` (its crate dependency too) with a one-line Linux stub that returns the reason; the Windows clippy and test jobs still build it.
- **WASAPI loopback reports an xrun on a fresh stream** (v0.6.76, #164): cpal's error callback gives `ErrorKind::Xrun` (the data-discontinuity flag) right after a loopback stream starts. Never treat every stream error as a dead stream: `dstack_endpoint::stream::needs_reopen` decides. Taking the xrun as fatal reopened dsend's capture every 5 s on resolume-snv, while the unit tests (simulated capture) were all green.
- **Our own multicast flows in tests** (#193): a whole-device test receives our flow's group with `dstack::media::rx::join(ip, group)` on the routed address (Linux loops a host's own multicast back to its members); the group is `media::tx::multicast_group(ip, process_id, slot)`. A guard that is followed by a stricter check (`unread == 0` before "exactly one record") is a mutant until a test passes the first check's failure alone: one good record beside an unread one (`list_reply_body` of two, the second offset set to 0xffff).
